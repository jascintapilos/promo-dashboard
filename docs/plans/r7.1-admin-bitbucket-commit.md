## Codex-locked architecture

| Decision | Choice |
|---|---|
| Auth | Repository Access Token, `repository:write` on `aiodintech/qc-dashboard` only |
| Commit target | Direct commit to `main` for **only** `admitted-users.json` — server never writes any other path |
| Concurrency | Optimistic: `{headSha, fileSha}` returned on load; POST fails 409 if either moved (see GET endpoint below) |
| Audit commit message | `admin-users: update allowlist by <actor-email>` + body with adds/removes/role-changes + source IP |
| Rollback | Skip first-class undo; git revert via Bitbucket UI is the recovery path |
| Fresh-auth | Save requires Google session issued within **15 min** — server checks `iat` claim in the original ID-token, stored in session cookie |
| Confirmation dialog | Typed-email confirm required for: any removal, any grant of `admin` role, any demotion of an existing `admin` |
| Rate limit | 20 saves per admin per hour, 60 per hour globally |
| CSRF | Double-submit cookie: server sets `qc_csrf` cookie on `/api/me`; client echoes header `X-CSRF-Token` on POST |
| MVP surface | Frontend Save button, not CLI-only |

## Server changes — `bin/qc-dashboard.mjs`

### New env var read at startup

- `BITBUCKET_REPO_TOKEN` — Repository Access Token. If unset and `AUTH_MODE!==dev`, log a warning at startup (server still runs — R7's Option B copy flow still works as fallback) but reject any `POST /api/admin/users` with 503 `bitbucket_token_missing`.
- `BITBUCKET_REPO_SLUG` — defaults to `aiodintech/qc-dashboard`. Read-only override allowed only when `AUTH_MODE==='dev'` OR `NODE_ENV==='test'`. In production the constant is used unconditionally.
- `BITBUCKET_API_BASE` — **Codex S2 fix**: hard-coded to `https://api.bitbucket.org/2.0` in production. Env-var override honoured ONLY when `AUTH_MODE==='dev'` OR `NODE_ENV==='test'` (blocks bearer-token exfiltration via a hijacked env var in prod). Any prod env-var override is ignored with a `console.warn`.

### Session cookie extension

**Codex S1 fix**: current sessions in `src/qc-dashboard/auth.js:98` already carry `iat` as `Date.now()` (**milliseconds**), used against `SESSION_MAX_AGE_MS` for the 8-hour expiry. A naive fresh-auth check on that ms-valued field, using `Date.now()/1000 - session.iat` in seconds, would treat every existing session as "fresh forever" (a 1.7 trillion-ms `iat` becomes a 1.7 trillion-second offset, well past the 15-min gate).

Solution: keep the existing `iat` field with its current semantics (cookie-mint ms, drives 8-hour expiry — unchanged). Add a **new** field `freshAuthAtMs` (ms) that captures the Google credential's original issued-at moment. Cookie shape becomes `{email, name, role, iat, freshAuthAtMs, exp}`.

- On real Google Sign-In: `freshAuthAtMs = googleIdToken.iat * 1000` (Google's `iat` is unix seconds; convert once at mint time).
- On dev-mode login: `freshAuthAtMs = Date.now()` (dev sessions are always "fresh" for admin actions since dev-mode also bypasses fresh-auth check).
- Fresh-auth check: `Date.now() - session.freshAuthAtMs <= 15*60*1000` — clearly ms on both sides.
- **Legacy sessions without `freshAuthAtMs`** (issued before R7.1 deploys): treated as **stale for admin POST** (401 `stale_session` with `re_auth_url: '/'`), still **valid for read-only** routes. No forced logout — the admin re-authenticates only when they try to Save. `loadHistory`, `/api/me`, `/api/brands` etc. continue to work on the old cookie until it expires normally after 8 hours.
- HMAC signing unchanged.

### New endpoints

#### `GET /api/admin/users`  (already exists — extended)

Now also returns `baseSha`:

```json
{
  "users": [{"email":"...", "role":"..."}],
  "headSha": "abc123def456…",
  "fileSha": "def456abc789…",
  "csrfToken": "…"
}
```

- **Codex S1 fix**: Bitbucket's `parents=<sha>` on `POST /src` is a **branch-HEAD** assertion, not a file-level one. If we use a file-level sha for `parents`, an unrelated commit that moved HEAD would fail with 409 even though our file didn't change. Return TWO shas:
  - `headSha` = tip of `refs/branches/main` via `GET {BITBUCKET_API_BASE}/repositories/{slug}/refs/branches/main` → `target.hash`. This is what MUST match `parents` at commit time.
  - `fileSha` = commit that last touched the file via `GET {BITBUCKET_API_BASE}/repositories/{slug}/src/main/admitted-users.json?meta=&format=meta` → `commit.hash`. Used ONLY for optimistic concurrency at the app layer (see POST gate #11 below).
  - Response body: `{ users, headSha, fileSha, csrfToken, warning? }`.
- Cache both shas 30s per-process to keep frequent modal opens cheap. Cache is invalidated on any successful POST (server writes the new headSha back to its cache).
- If `BITBUCKET_REPO_TOKEN` missing: return `headSha:null, fileSha:null` and add `warning: "bitbucket_token_missing_option_b_fallback"`. Frontend falls back to Copy-JSON behavior for this session.
- Sets CSRF cookie `qc_csrf` (HttpOnly=false, SameSite=Strict, path=/) with a fresh 32-byte hex token; response body echoes it as `csrfToken` for the initial handshake.

#### `POST /api/admin/users`  (new)

**Request:**
```json
{
  "users": [{"email":"...", "role":"..."}],
  "headSha": "abc123def456…",
  "fileSha": "def456abc789…",
  "confirmedRemovals": ["email1", "email2"],
  "confirmedAdminGrants": ["email3"],
  "confirmedAdminDemotions": ["email4"]
}
```

**Headers required:** `X-CSRF-Token` matching `qc_csrf` cookie. Missing/mismatched → 403 `csrf_check_failed`.

**Gate checks in this order (fail-fast, single 4xx per request):**

1. `requireSession()` → 401 if no valid cookie.
2. `user.role === 'admin'` → 403 if not.
3. Fresh-auth (see "Session cookie extension" above for unit rationale): `session.freshAuthAtMs` must exist AND `Date.now() - session.freshAuthAtMs <= 15*60*1000` → else 401 `stale_session` (response body includes `re_auth_url: '/'`). Legacy sessions with no `freshAuthAtMs` field always fail this gate.
4. CSRF match → 403.
5. Rate limit (per-admin: 20/hr; global: 60/hr) → 429 with `Retry-After`.
6. Payload size: refuse if body >64KB → 413.
7. `BITBUCKET_REPO_TOKEN` set → else 503 `bitbucket_token_missing`.
8. Server-side normalization + validation of `users`:
   - Each entry: `email` non-empty string, valid basic email shape (`/^[^@\s]+@[^@\s]+\.[^@\s]+$/`), role in the 4-role whitelist.
   - Reject unknown roles hard (never coerce on write — coercion only applies on load).
   - Reject entries with empty email.
   - Deduplicate by lowercased email; last entry wins.
   - Result must be non-empty and must contain **at least one admin** (prevents lockout).
   - If the incoming list has zero admins: 400 `at_least_one_admin_required`.

**Codex S1 fix — "at least one admin" must be defended in THREE places, not just here:**

- **Startup validation** (`validateAllowlist()` in `src/qc-dashboard/auth.js`): outside dev-mode, add an assertion that the loaded allowlist contains at least one admin. Fail-closed on startup if it doesn't. Reason: R7's manual Copy-JSON flow could already produce an admin-less file if the operator removed all admins by accident; today's validator only checks non-empty, not admin-present.
- **Server POST gate** (this step): already covered above.
- **Client Save button** (`public/qc-hub/app.js` R7 admin modal): Save/Copy JSON buttons disabled + tooltip "Keep at least one admin" whenever `state.adminUsers.filter(u => u.role === 'admin').length === 0`. Prevents the user from even trying — reduces round-trip errors and is the first line of defense.

All three defenses share the same rule; the server is authoritative but the client + startup catch it earlier for a better UX and cold-boot safety.
9. Diff computation vs current `admitted-users.json` (loaded from disk in dev, from Bitbucket in prod):
   - `adds` = emails in new not in current
   - `removes` = emails in current not in new
   - `roleChanges` = same email, role differs
   - `demotions` = emails whose role changed from `admin` to non-admin
10. Confirmation-arrays cross-check:
    - Every email in `removes` MUST appear in `confirmedRemovals`. Else 400 `confirmation_required` with list of missing confirmations.
    - Every email in `roleChanges` where new role is `admin` MUST appear in `confirmedAdminGrants`.
    - Every email in `demotions` MUST appear in `confirmedAdminDemotions`.
11. **Optimistic concurrency (see "GET" above for the two-sha rationale):**
    - `headSha` from request MUST match current `refs/branches/main` tip (freshly fetched, no cache). If not: 409 `stale_head` with current `{headSha, fileSha}` in body so client can reload.
    - `fileSha` from request MUST match current commit that last touched `admitted-users.json`. If not: 409 `stale_file` — same recovery flow.
    - Both checks matter: `headSha` mismatch means SOMEONE else pushed to `main`; `fileSha` mismatch means SOMEONE else edited THIS file. Client shows a different toast per case ("someone else edited the allowlist" vs "the branch moved").

**Commit (Bitbucket Data API):**

```
POST {BITBUCKET_API_BASE}/repositories/{slug}/src
Authorization: Bearer {BITBUCKET_REPO_TOKEN}
Content-Type: multipart/form-data

fields:
  admitted-users.json = <serialized file content, byte-for-byte from R7 formatter>
  message             = "admin-users: update allowlist by <actor-email>\n\n<adds/removes/role-changes summary>\nsource-ip: <X-Forwarded-For or remoteAddress>\ntrigger: qc-dashboard /api/admin/users"
  parents             = <headSha from the request, already validated at gate #11>
  branch              = main
```

**Codex S2 fix — omit `author`:** Bitbucket rejects unknown/non-workspace-member author identities with 400 `invalid_author`. Repository Access Tokens are not tied to a Bitbucket user, so any user-derived `author` string is a coin-flip. For MVP, skip the field entirely — Bitbucket auto-attributes the commit to the Repository Access Token identity. The actor's email is already in the commit `message` body for audit; no information loss. If we later want per-user attribution in git history, that's a separate feature that must first validate each admin's email against Bitbucket workspace membership before including it.

- 401/403 from Bitbucket → 502 `bitbucket_auth_failed` (mask token error details, log full response server-side)
- 409 from Bitbucket (stale parent) → 409 `stale_base_sha` (bitbucket saw newer HEAD after our check-and-commit window closed)
- 5xx from Bitbucket → 502 `bitbucket_upstream_error` with retry-after 30s
- 200/201 → server returns `{ok: true, newSha: <returned commit hash>, summary: {adds, removes, roleChanges}}`

**Success side effects:**
- Server logs `[admin-users] actor=<email> ip=<ip> adds=N removes=M role-changes=K new-sha=<sha>` to stdout (structured single-line JSON also works — pick one and stick to it).
- The auto-deploy pipeline picks up the new `main` commit within 30-60s; the running server's in-memory allowlist refreshes on the next `SIGHUP` or process restart (already how deploy works today; no new hot-reload path needed).

### Non-endpoints

- No new file-write paths. Server does not write to `admitted-users.json` on disk; the deploy re-pulls from git.
- No admin-facing "who is currently logged in" endpoint.
- No token rotation endpoint (rotate manually via Bitbucket UI + variable update).

## Frontend changes — `public/qc-hub/app.js` + `index.html`

### `openUsersModal()`

- Fetches `/api/admin/users`; stores `baseSha` and `csrfToken` on `state`.
- Renders warning banner if `warning === 'bitbucket_token_missing_option_b_fallback'` — modal falls back to R7 Copy-JSON flow (hides Save button, shows Copy button).

### New "Save changes" button

Placed alongside the existing Copy button. Enabled only when the local edited list differs from the loaded snapshot (compute diff on every add/remove/role change).

Click flow:

1. Compute diff (adds/removes/roleChanges/demotions).
2. If nothing to save: no-op with muted status text.
3. If removes.length + adminGrants.length + demotions.length > 0: open **confirmation sub-modal** listing the changes and requiring the admin to type each affected email into a text field before Save is enabled. (One field per confirmable email; all must match exactly.)
4. POST `/api/admin/users` with `{users, baseSha, confirmedRemovals, confirmedAdminGrants, confirmedAdminDemotions}` and `X-CSRF-Token` header.
5. Success: close modals, show green toast "Saved. Auto-deploy will apply changes in ~60s."
6. 409: show yellow toast "Someone else updated the allowlist while you were editing. Reloading current state." Auto-reopen modal with fresh `baseSha` and preserve the admin's uncommitted local edits (merge: keep admin's edits on top of new base, re-diff, re-confirm).
7. 401 stale_session: show modal "Session too old for admin actions. Please sign in again." with a Sign In button linking to `/`.
8. Other 4xx/5xx: red toast with the server's error code + short message.

### CSRF plumbing

- On first successful `/api/me` load in `ensureLogin()`, read `qc_csrf` cookie via `document.cookie` and stash on `state.csrfToken`.
- Every POST includes `X-CSRF-Token: state.csrfToken` header.
- No cookie parsing helper library — one-liner using `document.cookie.split('; ').find(c=>c.startsWith('qc_csrf='))`.

### Confirmation sub-modal DOM

- Built with `document.createElement()` + `textContent` — no `innerHTML` on admin data (same R7 XSS rule).
- Type-to-confirm inputs use `type="email"` for browser hint, but the equality check is strict string comparison against the lowercased email.

## Safety constraints (non-negotiable)

- No new npm dependencies
- No new secrets beyond `BITBUCKET_REPO_TOKEN`
- `BITBUCKET_REPO_TOKEN` scope: `repository:write` on ONE repo. No admin, no pipeline, no wiki. Verify in Bitbucket UI before variable entry.
- Token never logged, never returned in response bodies, never in error messages surfaced to client
- CSRF token: HttpOnly=false (client must read it), SameSite=Strict, path=/, regenerated on each `/api/me` call
- Rate limits enforced server-side; frontend hints match but never trusted
- Server never writes to any file path other than `admitted-users.json` in the Bitbucket commit
- Server never blindly trusts client's normalized list — always re-normalize + re-whitelist server-side
- Nothing pushed to `main` from Claude's changes without user diff review + explicit approval
- If Bitbucket API returns anything other than 200/201/409/5xx, treat as failure (never assume partial success)
- Existing session cookies without `iat` are treated as "stale" for admin actions but still valid for read-only routes — no forced re-auth for regular users
