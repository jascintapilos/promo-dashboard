WS1 and WS2 `PromotionName`/`RewardName` values must be **unique** per BO site at save time. Duplicate names create real downstream confusion.

**Why:** The Manual Reward Assignment team assigns rewards to members via the "Assign Rewards" modal on a Player's page, a drop-down populated from `/PM/GetActivePromotionRewardsByPlayer` and keyed on **`PromotionReward.RewardName`** — NOT `Promotion.PromotionName` (correcting an earlier version of this note). These are two *separate* fields on two different objects. If two rewards share the same `RewardName` on the same BO, the assigner can't tell them apart and assigns the wrong one — wrong reward, wrong T&C, wrong rate.

**Fixing an existing collision requires TWO API calls, not one** (confirmed live 2026-07-03 on WS2):
1. `/PM/UpdatePromotionDetails` — sets `Promotion.PromotionName` (the name shown in list/search views).
2. `/PM/UpdatePromotionRewardDetails` — sets `PromotionReward.RewardName` (the name shown in the Assign Rewards dropdown). Payload: `{RewardId, RewardName, RedeemableQuantity, CapBonusAmount, RedeemableKYCStatus, WithdrawalCap, MaximumBalance}` for Bonus/FreeSpin; Free Credit adds `DepositRequirement, RequiredApprovedDeposit, DepositPeriodicDays`. Read current values from `GetBonusInfo`/`GetFreeCreditInfo`/`GetFreeSpinPromotionInfo` first and pass everything through unchanged except `RewardName` — this endpoint is a full-replace on that field set.
   **WS1 v3 payload typing quirk (confirmed live 2026-07-04, 42 promos on kioskmy):** all numeric values must be sent as **strings** and `RedeemableKYCStatus` as a **CSV string** (`"BASIC,ADVANCED,PRO"`), not an array — the WS2-style payload (numbers + array) returns an empty-body HTTP 500 on WS1 v3. Same values-as-strings pattern as `UpdateBonusDetails`/`RedeemableDay`. Working recipe: `bin/_rename-ws1-tleo-rewardnames.mjs`.

In the live "Edit Promotion" UI, both calls fire together off one Save button (one `txtPromotionName` input feeds both), which is why this is easy to miss when scripting an ad-hoc rename — only calling #1 leaves the Reward-assignment dropdown stale.

**Core reward economics are immutable post-creation** — see [[project_ws2_free_credit_rollover_immutable]]. `RolloverMultiplier`, `BonusPercentage`, `FixedBonusAmount`, `MinimumActionAmount` cannot be changed via `UpdatePromotionRewardDetails` even by over-posting the fields; the server silently ignores them. If a naming fix reveals the underlying config doesn't match what was approved (e.g. code/description say "TO5x" but live is "TO0x"), that's a separate, harder problem — deactivate + recreate, don't try to patch it in place.

**How to apply:**
- Before any IGMP `--commit` save, probe each target site for existing promos with the candidate name.
- Names today are generated by `api-mapper-igmp.js` as `"<base> (MIN<x> / CAP<y> / TO<z>x)"`. Distinct rate × min-dep × cap × TO combinations naturally diverge, but repeat campaigns of the same shape collide — and so do reward-tier ladders created ad hoc outside the mapper (e.g. a batch of "VIP Exclusive Offer - 50% Reload Bonus" promos with no differentiator in the name at all).
- If a collision is found:
  1. STOP and surface the collision to the operator.
  2. Confirm next move (e.g. append `(MIN<x> / CAP<y> / TO<z>x)`, a segment tag like `(Active-High/Churned-Low)` when reward config alone doesn't disambiguate, or a date/RN suffix) — do not silently rename.
  3. Check whether the promos are **true duplicates** (identical config in every field) before fabricating a distinguishing suffix — inventing a fake difference is worse than leaving the collision, since it misleads the assigner into thinking there's a real distinction. Flag true duplicates to the operator instead of renaming them.
- Only applies to **WS1 / WS2 (IGMP)**. QPRO + QP2 are not affected (BO identifies by code, not name).
- **2026-07-04:** the entire TLEO family on WS1 MY (42 promos, 5 shared names) was deduped with code-derived suffixes `(LC|SLOT / CAP<n> / BR)` — both PromotionName and RewardName. Scripts: `bin/_rename-ws1-tleo-unique.mjs` (pass 1) + `bin/_rename-ws1-tleo-rewardnames.mjs` (pass 2). ~36 legacy duplicate-name groups remain on WS1 MY (Genting/Optimove/VM/TEST etc.) — untouched, pending operator direction.
- **`FT_REL_TLEO_45PCT_458MX` (id 3616, WS1 MY) — code/name mismatch is INTENTIONAL:** the code says 458 but the live `CapBonusAmount` is 450, and the operator ruled the 450 cap is correct. Its name is `... (CAP450)` on purpose — the name follows the live cap, the code does not. Do not "fix" the name back to CAP458 or flag this in QC.
